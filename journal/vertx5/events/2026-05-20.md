## 2026-05-20 14:49

- Found root cause of MixReactiveTransactionalTest failure on Vert.x 5 branch, working with Julien Ponge. On Vert.x 5, ContextInternal.putLocal() and ContextLocals.get() use different backing storage. In Vert.x 4 both pointed to the same ConcurrentHashMap. In Vert.x 5 ContextInternal.putLocal() writes to ContextInternal.LOCAL_MAP, while ContextLocals uses a separate per-type array-based storage from smallrye-common.
- The reactive transaction interceptor (TransactionalInterceptorBase.java:87) writes TRANSACTIONAL_METHOD_KEY via ContextInternal.putLocal() but the guard reads via ContextLocals.get(), so the check that detects @Transactional calling @ReactiveTransactional never finds the key. Instead of the expected error message, Hibernate Reactive hits HR000091 (duplicate active transaction), HR000090 (live transaction on close), and NPE on Transaction.rollback().
- Fix: use ContextLocals.put()/get() consistently instead of ContextInternal.putLocal(). Same pattern already used by Clement Escoffier in commit 7fb1e03. Eventually Hibernate Reactive should also migrate to ContextLocal (the Vert.x 5 native API with per-type registration and duplication control) but ContextLocals from smallrye-common is the right transitional approach.
